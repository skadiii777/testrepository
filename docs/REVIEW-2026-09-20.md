## 二、必须优先处理的 4 项

### R1 · 移动端 `enterprise-pro-app` 完全没有远程备份 🔴

- 实测：`git remote -v` **输出为空**；分支仅本地 `master`（2 个提交：`6bcdb4c`、`6421ede`），工作区干净
- 该应用**已在生产环境运行**（nginx `/m/`，见 `enterprise-pro/AGENTS.md:16`），12 个页面（login/index/leave/expense/correction/report/approval/chat/chatroom/message/mine + App.vue）
- 风险等级与 09-15 前端事故同级，且更严重：前端当时至少已推送到远程，移动端是**纯单点**
- 另：`package.json` 仍是 uni-app 模板默认值 —— `name: "uni-preset-vue"`、`version: "0.0.0"`、无 `description`
- 建议：立即建远程（可并入 testrepository 的独立分支或新建仓库）并推送；同步补齐 `README.md`

### R3 · 一个远端仓库承载三条互不相关的历史 🟠

实测 `git ls-remote --heads`（testrepository）：

```
c3e78f1…  refs/heads/main     ←  enterprise-pro 后端
a9a6348…  refs/heads/master   ←  旧 enterprise-ms
7fa85ab…  refs/heads/pro-ui   ←  enterprise-pro-ui 前端
```

- 已实测：`main` 对应后端提交 `c3e78f1`（"fix: lombok 版本对齐"），正是后端仓库中的一个提交
- 这正是 09-15 前端推送失败的根因（浅克隆薄包假定远端已有父提交，而远端装的是后端历史 → `index-pack failed`），见 `enterprise-pro-ui/AGENTS.md:16`
- 后果：clone/pull/fetch 语义混乱、误 fetch 会灌入无关对象、"某分支被覆盖"类事故概率上升
- 建议：后端、前端、移动端各自独立仓库；若因配额不想拆，至少用**分支命名空间**并写进文档

### R4 · 前端项目的规矩文件未纳入版本控制 🟠

`enterprise-pro-ui` 的 `git status` 有三个 **untracked** 项：

```
?? .github/
?? AGENTS.md
?? CLAUDE.md
```

- 后端 `enterprise-pro/AGENTS.md` 已入库，前端没有
- 前端 AGENTS.md 里恰好存着 09-15 两次事故的教训与"删除前二次确认""新页面必须浏览器实测"等硬规矩 —— **这些知识此刻只存在于本机磁盘**
- 另：前端 `github/pro-ui` 的 remote-tracking ref 已丢失（`git branch -vv` 显示 `[github/pro-ui: gone]`），但远程分支**实际存在**（`7fa85ab` = 本地 HEAD）。需 `git fetch github` 修复跟踪关系，否则会被误读为"没推上去"
- 前端 `origin` 仍指向 gitee 上游 `yudaocode/yudao-ui-admin-vue3`（09-15 建议改指自有仓库，未执行）
